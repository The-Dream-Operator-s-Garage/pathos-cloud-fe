# pathos.cloud Dashboard UI Reference

> Canonical reference for the dashboard layer. For *how* the dashboard mirrors the API + which architectural role it plays, see [docs/architecture/dashboard.md](../../docs/architecture/dashboard.md). For design rationale, see [docs/concepts/](../../docs/concepts/).

Quasar v2 (Vue 3) | Javascript | SCSS | Webpack | Axios

## Setup (after `npm init quasar`)

When running `npm init quasar` from project root choose:
- App with Quasar CLI
- Project folder: `dashboard`
- Quasar version: Quasar v2 (Vue 3)
- Script type: **Javascript**
- Quasar App CLI variant: **Webpack**
- CSS preprocessor: **Sass with SCSS syntax**
- Features: **Axios, Vue-Router, Pinia, ESLint**
- ESLint preset: Standard

Then replace/add the pre-built files in `src/`.

## Service mirror (src/services/)

Each frontend service is a thin axios wrapper around one backend resource. Conventions:
- Return the raw API payload (`{ success, ...payload }` or `{ success: false, error }`).
- Components handle both shapes inline.
- The axios instance lives in `services/api.js` with a request-interceptor that injects the JWT and a 401 interceptor that clears auth + redirects to `/auth`.

### File tree viewer

`/files` renders the on-disk pathchain (`files/<owner>/…`) as a recursive tree. Backed by `services/file.service.js` → `/api/files`.

| Component | Role |
|-----------|------|
| `pages/FileTreePage.vue` | ⭐ Page shell: loads the tree, lineage breadcrumb, and builds the intra-tree **nav controller** (see below). |
| `components/files/FileTreeNode.vue` | Recursive row. Folders expand inline; each leaf carries a Mini-preview dropdown + a decoded/`.proto` dropdown. Consumes the nav controller to force-open + flash a revealed element. |
| `components/files/DecodedContentInline.vue` | The decoded panel: a **draggable vertical `q-splitter`** — decoded JSON leads at 70%, the `.proto` schema trails at 30% (stacks on phones). |
| `components/files/JsonView.vue`, `JsonNode.vue` | Collapsible pretty-printed JSON. `JsonNode` renders any reference-address string as a `RefChip`. |
| `components/files/RefChip.vue` | ⭐ A `MicroChip` whose click **reveals the target inside the tree** (`treeNav.reveal`) instead of routing away. |
| `components/files/FileContractBadge.vue` | Contract verdict chip for FILE nodes (mounted in `NodeDetailPage`'s body-kind row). Lazily calls `GET /api/uploads/verify/…` via `services/upload.service.js` and renders **contract verified** (teal carved chip, `.pioneer-gold` relief pattern) or **contract violated** (red) — the on-disk sealed container's word on whether the bytes still match the node. Hidden on transport errors. |
| `utils/treeNav.js` | The nav controller factory. Indexes every leaf by canonical `<prefix>/<hash>`, force-opens ancestor folders, scrolls + flashes the target, and auto-expands its decoded panel. |

**Intra-tree navigation flow:** open a leaf's decoded dropdown → every `kind/hash` reference field (author, register, tag, head, prev/next/target, …) is a `RefChip` → click it → `FileTreePage`'s provided `treeNav` resolves the address in its index, force-opens the ancestor folders, scrolls the target row into view, flashes it, and auto-expands *its* decoded panel. Targets outside the loaded subtree (e.g. a cross-owner reference on `/files/:ownerHash`) fall back to `/files?reveal=<address>`, which resolves on the whole-platform view. Plain-content fields (`text`) and empty fields stay inert text — only `parseRef`-matching addresses become chips.

## Routing + auth

`router/routes.js` plus `router/index.js` (the guard). The guard:
- Allows unauthenticated visits to `/auth/*`.
- All other routes require `auth.store.token`. On entry it triggers `/api/identity/verify` (single check on app boot via `App.vue`). On 401 the api.js interceptor clears localStorage and routes to `/#/auth`.

## API connection

`src/services/api.js` reads `process.env.API_URL` (default: `http://localhost:3000/api`). Set via `quasar.config.js` `build.env.API_URL` for different environments.

## Keylogger stub

The typing session keylogger for NOTE nodes is stubbed at the data model:
- DB: `node` table has `content TEXT` and `ancestor_id` for versions.
- A `KEYSTROKES` skeleton kind is *planned* but no service writes to it (see [docs/concepts/skeletons.md](../../docs/concepts/skeletons.md) and [docs/gaps/contradictions.md](../../docs/gaps/contradictions.md) #10).
- UI: the makers' note editors (`MakerDock`, `UploaderDock` Write mode) do not yet track keystrokes.
